## 资源未达到容量上限的修复

用户报告电量停在199.95 / 200。新增测试在旧引擎稳定复现：新档推进600秒后内部库存为199950，容量为200000；零件先回收、后被记录员使用时，库存也会停在容量减去该秒消耗的位置。界面直接显示库存，内部使用整数；根因是先按当前仓储余量截断生产、再扣后续消耗，提前丢弃了该秒仍可利用的产能。

修复保留正常供给与岗位优先级，在同秒工作和预留后复用因满仓而未使用的产能预算，按记忆、零件、电量顺序补充。累计投入取整后扣除已支付部分；预算不跨秒、不超过原有产能，不把缺料或产能不足的库存强制补满。记忆通常没有持续消耗，但同秒后续工程预留腾出的空间也使用这套规则。

新增4项引擎测试验证精确上限、零件与电量同秒补充、分次生产投入取整、工程预留与供给不足。原有优先级、满仓停工、分段等价、离线报告与存档守恒测试全部通过。最新完整结果为30项单元/存档测试、11项浏览器测试，类型检查与构建通过。

桌面与手机均通过实际界面到达电量300 / 300、零件250 / 250、记忆80 / 80，三条资源进度条实际宽度均为100%。浏览器读取合法的199.95旧档后推进到200 / 200，再保存和重开仍保持满仓。存档结构和数值版本不变，不需要清档。

## 引擎/浏览器场景

UT-01–UT-14及BT-01–BT-08都有对应测试。1小时、24小时和7天引擎推进实测通过；容量修复后7天引擎场景在本机约1.1–1.4秒完成，浏览器验证含界面启动与结果对比约1.5秒。长结算按批次让出浏览器处理时间。

存档结构当前仅支持版本1、数值版本0.1.0；没有历史版本需要迁移，未知版本明确拒绝覆盖。后续引入新结构必须补迁移与旧档测试。

浏览器验证使用Chromium；未验证Safari、Firefox或真实触摸设备。扩大正文检查不等于全面浏览器缩放验收。数值节奏记录来自自动化路线，尚无真人试玩或长期平衡证据。
