## 1. 技术路线选择

| 方案 | 优点 | 适用判断 |
| --- | --- | --- |
| TypeScript + 原生页面 | 依赖少，适合小型单页原型 | 首章节快速试验可用，后续多页面和状态交互需自行组织 |
| TypeScript + React + Vite | 适合资源表、队列、档案与复杂状态的组件化维护 | 推荐，能够承接长期扩展 |

推荐基线：

- **TypeScript**：为资源、事件、存档和规则建立明确的数据类型。
- **React**：组织界面组件与交互。
- **Vite**：提供开发与构建工具。
- **原生CSS**：响应式排版、明暗主题与文字表现。
- **Vitest**：验证经济、时间与存档规则。
- **Playwright**：验证实际浏览器中的核心流程、存档与多标签页行为。
- **浏览器本地存储**：保存首版单人进度，配套导入与导出。

依赖版本在建仓启动时根据官方说明、现有Node.js环境和包兼容性确定，随后提交锁文件。当前文档不预设具体版本号。

首版运行与保存均由浏览器完成。后续账号、跨设备保存或多人功能需要单独的产品范围与系统设计。

~~~mermaid
flowchart TD
    A["界面：资源、岗位、工务、档案"] --> B["动作处理与应用控制器"]
    B --> C["独立游戏引擎"]
~~~

同一引擎负责在线推进、后台补算、离线结算和自动化测试。经济规则只有一个来源。

## 4. 数据模型

### 4.1 核心状态

| 模型 | 最少需要记录的内容 |
| --- | --- |
| ResourceState | 当前库存、历史取得、生产、奖励、运行消耗、工程预留与取消返还统计 |
| FacilityState | 设施ID、当前等级 |
| PopulationState | 各类居民总数、到达计时 |
| AssignmentState | 各居民类型在四种岗位的分配 |
| PolicyState | 照明策略、首次免费选择是否已使用 |
| ProjectState | 唯一ID、定义ID、目标等级、状态、工程进度、预留费用 |
| ResearchState | 已完成研究ID |
| EventState | 已触发、待选择、已选择、待领取、已领取 |
| UnlockState | 已开放功能与首章节状态 |
| PriorityState | 回收、维修、记录的顺序 |
| ClockState | 累计模拟时间、不足1秒的余量、最近结算时间 |
| SettingsState | 主题与显示偏好 |
| ReportState | 尚未确认的返回报告摘要 |
| SequenceState | 用于生成居民、项目等对象ID的序列 |

容量、净产出、岗位上限和可负担状态由配置与当前状态推导，避免同时保存多份互相矛盾的结果。

### 4.2 数值精度

- 资源使用定点数（fixed-point）：内部1000表示界面上的1单位。
- 人口、岗位人数、设施等级使用整数。
- 工程进度使用同一明确精度，维修产出允许小数。
- 产出倍率在统一位置计算，统一量化规则。
- 每秒产出计算量化到0.001单位，量化误差在试玩记录中观察。
- 界面显示可保留1–2位小数；判断可负担使用内部精度。
- 建设费用按产品规则向上取整到资源整单位；取消返还按产品规则向下取整。

### 4.3 状态不变量

任意操作与推进后，必须满足：

1. 资源非负且不超过当前容量。
2. 分配人数不超过对应类型居民总数。
3. 各岗位不超过设施提供的容量。
4. 设施等级处于0–3之间。
5. 工务队列不超过3项。
6. 只有一个项目处于运行状态；暂停项目保留其预留费用与进度。
7. 已完成项目、研究、事件领取不会重复应用。
8. 游戏累计模拟时间不回退。
9. 同一设施最多有一项未完成的建设或升级。
10. 同一一次性主线工程或研究不能重复入队。

类型检查与运行时校验各自负责开发错误和外部存档数据。

## 5. 引擎接口

建议接口的语义：

| 接口 | 职责 |
| --- | --- |
| createGame() | 按配置生成新档 |
| advance(state, elapsedMs) | 按既有安排推进，返回新状态与变化摘要 |
| applyAction(state, action) | 应用已验证的玩家操作，返回结果或明确失败原因 |
| deriveView(state) | 推导产能、容量、费用、等待原因与界面状态 |
| encodeSave(state, metadata) | 生成版本化存档 |
| decodeSave(text) | 解析、校验、迁移，返回有效状态或错误 |

引擎内部不调用系统当前时间、不读写浏览器存储、不操作页面。时间、动作和数据显式传入。

首版事件与居民到达是确定性的。同样的状态、经过时间与操作序列得到同样的游戏结果。

## 6. 时间推进与离线结算

### 6.1 统一逻辑步

基础推进使用1秒逻辑步（tick）：

1. 将elapsedMs与上一轮不足1秒的余量合并。
2. 计算完整逻辑秒数，并保留剩余毫秒。
3. 逐步处理生产、供给、工程与居民到达。
4. 检查确定性解锁与事件触发。
5. 汇总生产、消耗、完成项目与停工信息。

同一个逻辑秒的顺序固定：

1. 推进模拟时钟。
2. 发电提供库存。
3. 尝试维持照明，确定本秒策略是否生效。
4. 按玩家优先级处理回收、维修、记录。
5. 利用同秒消耗与工程预留腾出的空间，补充因容量不足未使用的本秒产能；按记忆、零件、电量顺序处理，覆盖补产本身的投入消耗。
6. 更新居民到达计时。
7. 检查工程成果、功能解锁与事件。
8. 检查状态不变量，累积报告。

工程费用只在开工时从库存预留；运行耗电属于持续生产支出。暂停时停止该项目的运行耗电。

库存记账满足：结束库存 = 开始库存 + 实际生产 + 已领取奖励 + 实际取消返还 - 运行消耗 - 新工程预留。完成项目时不再次从库存扣除已预留费用。累计取得只增加实际生产和已领取奖励，取消返还不影响成长解锁的历史门槛。

### 6.2 容量与缺料

每项工作的实际产出由以下条件共同决定：

- 实际工作人员及其类型。
- 设施、策略与研究倍率。
- 电量和原料是否足够。
- 产出资源剩余容量。

存在部分供给或部分剩余容量时，产出和对应消耗按同一比例降低。所有取整集中处理，避免分别取整产生负库存或免费产出。

每秒保留因容量受限未使用的产能预算，在正常优先级分配后最多补充一次，不重新计算或增加该秒的产能。原料不足而未达到容量边界的工作不重试。同秒分次生产的投入按累计实际产出计算向上取整值，再扣除已支付投入，避免重复取整多扣资源。未使用预算不跨秒保存、不计入累计取得；实际入库与消耗继续按账本记账。

### 6.3 工程完成与事件

- 项目跨越完成边界时，只结算到所需工程量。
- 设施等级、研究和主线成果在完成时原子应用，即作为一个不可拆分的状态更新。
- 下一项从下一逻辑秒开始处理。
- 有明确选择的事件只进入待处理列表。
- 事件解锁与奖励状态分开保存。
- 变化摘要记录完成项目，避免为每个逻辑秒生成日志。

### 6.4 长离线的计算

首版验证1小时、24小时、7天经过时间的结算。

基础正确性以统一逻辑步为准。长结算可分批执行，保持页面响应并显示进度。必要时使用浏览器后台计算线程（Web Worker），由完整状态和经过时间得到结果。

当长期离线成为具体性能瓶颈时，可以对稳定生产区间进行批量推进。优化必须保留工程完成、容量变化、资源耗尽、到达与事件边界，并通过分段推进等价测试。

离线结算完成后，将状态与对应结算时间一起保存。结算失败时，保留最近有效存档，允许重新读取同一待结算时间段。

### 6.5 关键等价性

同一初始状态和不含中途玩家动作的时间段：

> 连续推进1小时 = 分60次推进1分钟 = 离线推进1小时。

比较库存、工程进度、设施、人口、事件、奖励记录与时间余量。变化报告中的生产和消耗也应可累加得到相同结果。

## 7. 玩家动作与业务规则

| 动作 | 关键验证 |
| --- | --- |
| 调整岗位 | 居民余量、岗位容量、类型ID |
| 调整优先级 | 完整且无重复的岗位顺序 |
| 工程入队 | 解锁、等级上限、唯一性、队列容量 |
| 重排队列 | 只移动未开工项目 |
| 暂停 / 继续 | 当前项目状态、已保存进度 |
| 取消项目 | 返还比例、当前容量、玩家确认 |
| 切换照明 | 已解锁、费用足够、首次免费状态 |
| 选择事件 | 已触发、尚未选择、选项有效 |
| 领取奖励 | 唯一性、当前容量 |
| 导入存档 | 格式、版本、数值范围与状态不变量 |

动作发生前，控制器先把当前状态推进到动作时间。这样暂停、修改人手或更换照明只影响后续时间。

同时到达的动作由控制器串行处理，保持资源扣费与状态修改顺序明确。

## 8. 存档、恢复与多页面

### 8.1 存档信封

~~~json
{
  "format": "districtzero",
  "schemaVersion": 8,
  "balanceVersion": "0.5.0",
  "savedAt": 0,
  "state": {}
}
~~~

这是当前线上及本地V0.5的信封格式示意；此前本地V0.4为结构7/数值0.4.0，历史公开V0.3.3为结构6/数值0.3.3。schemaVersion记录结构版本，balanceVersion记录数值配置版本。真实state包含完整游戏状态、最近实际结算时间与模拟余量，示意中的空对象不能作为有效存档导入。真实结构1–7使用各自来源边界校验与明确迁移；结构8不能导回旧版V0.4或V0.3.3。存档键与写入锁保持不变。

### 8.2 保存策略

- 浏览器主存档键建议为districtzero.save.v1。
- 恢复副本键建议为districtzero.save.backup.v1。
- 正常运行暂定每10秒保存；关键动作和离线结算完成后立即保存。
- 隐藏页面时尝试保存，但不能只依赖关闭页面事件。
- 新状态有效且写入成功后，界面才显示保存成功。
- 保留最近有效恢复副本，避免用坏数据覆盖可恢复的进度。
- 浏览器存储不可用时，明确显示保存失败，并继续提供导出当前有效状态。

### 8.3 导入与迁移

1. 读取文本与JSON结构。
2. 检查format、版本与数据范围。
3. 支持的旧版本执行明确迁移。
4. 重新计算推导数据，检查状态不变量。
5. 展示导入摘要与替换范围。
6. 确认后保存现有恢复副本，应用新状态。

未来版本无法识别时，拒绝自动覆盖并说明版本不兼容。`SaveVersionError`区分版本不兼容与普通损坏；加载不兼容主档时不回退到旧副本，普通保存也会再次检查版本。只有已确认的有效导入或重置使用`replaceIncompatible`允许替换；长离线补算沿用该次确认的保存选项。恢复与导出均使用数据格式，不执行存档中的代码。

返回报告的完工记录与名称显示共用`parseCompletionKey`校验街区、工程、设施与等级；V0.1报告只接受当时已有的标识。历史报告不要求设施仍存在，允许在拆除后保留完工记录。名称显示遇到未知标识时保留原文，避免配置查找失败导致白屏。

### 8.4 多标签页

同一浏览器的所有页面共用运行会话锁。采用浏览器提供的锁能力，由会话适配器管理所有权与释放。

- 主页面负责推进与保存。
- 其他页面显示已有运行页面，并停止写入。
- 主页面关闭后，另一页面获得锁，重新读取存档并补算。
- 锁释放与切换是一个可验证的流程。
- 导入、恢复、重置均需处于主页面会话。

实现前检查目标浏览器的锁能力与兼容性；若需要兼容替代方式，应采用可验证的互斥机制，并覆盖双页面竞争测试。

## 9. 界面实现方案

### 9.1 组件职责

- ResourcePanel：库存、容量、净变化、来源明细。
- WorkerPanel：两类居民、空闲人数、岗位分配。
- FacilityList：设施等级、效果、费用、可用状态。
- ProjectQueue：顺序、进度、预留费用、操作与等待原因。
- PolicyControl：照明效果、维护与切换费用。
- EventInbox：事件、选项和奖励。
- ArchivePage：居民、研究、事件和地址记录。
- ReturnReport：离线成果、流量统计和停工解释。
- SettingsPanel：保存、导入、导出、主题与重置。

生产推进不依赖组件渲染次数。界面订阅必要的状态摘要，长结算期间显示处理状态，避免每个逻辑秒刷新整个界面。

### 9.2 视觉基线

- 以文字和信息密度为核心。

## 14. 主要交付风险与处置

| 具体风险 | 处置与验证 |
| --- | --- |
| 离线与在线计算产生不同资源 | 共用引擎与逻辑步，执行分段等价检查 |
| 缺料或满仓导致输入仍被完整扣除 | 产出与投入同比缩放，覆盖容量与耗尽边界 |
| 多页面重复推进并覆盖存档 | 会话互斥、接管时重读有效存档 |
| 事件与研究在恢复后重复生效 | 稳定ID、已应用记录与恢复测试 |
| 等待过长且缺乏选择 | 试玩记录瓶颈，调整成本、岗位与阶段目标 |
| 长离线计算影响页面操作 | 分批或后台线程；必要时优化稳定区间并验证等价 |
| 后期功能让初级操作不断增加 | 分阶段自动化与配置模板，持续检查操作负担 |
| 初始数值缺少实际验证 | 配置化并保留试玩证据，禁止以文档推导代替体验结果 |

## 17. V0.3的实际扩展

- `src/game/network.ts`定义雨城/长站的独立库存、配方、运量、运行费用、磨损与运输规则。模块不访问界面、存储或系统时钟；引擎传入本城容量与记录回调，避免循环依赖。
- `GameState.network`保存两地库存及收到/生产/消耗/发出账本、路线状态、外派人员、在途运单、合同、优先级、运单序列和维护计数。共享车队是可用运力池，每条线最多一辆占用；本版不模拟每辆空车的物理停靠位置。
- 发车先检查人员、车队、整车容量、来源库存、当前目的地空间、线路与运行费用；成功后装车扣库、扣电并磨损。运单固定本次时长与货物，到货才入目标库存，途中满仓则整车保留。重复发车、重复卸货不会重复扣取或增加物资。
- 本城生产、工务预留、同秒补产与完工后，按线路处理到站/卸货、外部配方，再按优先级尝试自动合同，最后触发事件。配方缺料或满仓保留已准备的周期，不部分扣料。在线、后台与离线仍共用每秒逻辑。
- `freeResidents`扣除按原住处统计的外派人手；岗位、迁居和模板使用同一余量。外派不改变人口或入住序列。线路维护使用`route:rain`、`route:station`工程，参与原工务队列、预留、暂停、取消与退款规则，完成只增加维护次数。
- 本城账本增加`exports`与`imports`；进口不增加`earned`。报告使用两类运输流量解释库存变化，另外统计发车、到货和线路维护。本城、外部节点、配方与在途货物共同校验守恒；到货次数可能超过本次发车数，因为返回前已有列车在途。
- 结构3/数值0.3.0兼容结构1/0.1.0和结构2/0.2.0。旧状态先受原版内容限制校验，再加入空夜网与零运输账本/报告计数。存档验证检查城市容量、整份配方/货物、车队、人员重叠、运单时间、序列及两端收支；未知版本保护沿用V0.2审查修复。
- `src/ui/Network.tsx`提供外派、双向发车、实时货物与城市库存、合同保留量、批量、线路优先级和维护。`App`接入第三章目标、事件、研究、报告与存档说明，沿用桌面/手机布局。

验收N01–N08由`tests/unit/network.test.ts`与`tests/browser/network.spec.ts`验证，真实V0.2/V0.3章节样本保留在`tests/fixtures/`；具体结果见[验证记录](VERIFICATION.md)。未新增依赖。V0.3及合同审查修复已提交、推送并发布到[GitHub Pages](https://lxjmaster.github.io/DistrictZero/)，公开页面与验证构建一致。
